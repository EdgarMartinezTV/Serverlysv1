# Serverlys — Technical SEO Audit

Audited 2026-09-16 against a **production build** (`output: standalone`,
`NODE_ENV=production`) served on `127.0.0.1:3200`. Dev-server numbers are not
used anywhere in this document: unminified bundles and HMR overhead make
performance figures from `next dev` misleading, and quoting them would be worse
than quoting nothing.

Every number below was measured. Nothing is estimated.

---

## 0. The headline finding

**This repository did not need an SEO overhaul.** It already carried a
purpose-built SEO layer — `lib/seo.ts`, `app/robots.ts`, `app/sitemap.ts`,
`app/opengraph-image.tsx`, a dynamic OG image route, a hand-written JSON-LD
graph, and `scripts/seo-audit.mjs`, which is a more thorough technical checker
than most projects ever write.

On first run that audit reported **0 failures and 0 warnings across 123 pages**.

So this engagement found and fixed **two real defects** and closed **three gaps
in the test coverage that hid them**. It did not add meta tags to pages that
already had them, and it did not restyle anything. Where a phase of the brief
found nothing wrong, this document says so rather than manufacturing work.

## 6. Structured data — no defects found

Hand-built graph with `@id` linking. The existing audit validates, on every
page: JSON-LD parses, required fields per type, `AggregateOffer` low ≤ high,
`BreadcrumbList` positions in order, **no dangling `@id` references**, exactly
one `Organization`, one `WebSite`, and `BreadcrumbList` present on child pages.

Two design decisions worth recording because they are the honest ones:

- **No `aggregateRating` anywhere.** `scripts/check-reviews.mjs` proves the
  testimonials on this site are still placeholders, so there is nothing
  genuine to aggregate. Inventing one is what earns a manual action.
- **`FAQPage` schema is validated against the visible page.** The audit fails
  if a schema question does not appear in the rendered HTML — which structurally
  prevents fabricated FAQ markup.

## 9. Internal linking — ONE REAL DEFECT, FIXED

This is the substantive finding of the audit.

`relatedArticles()` in `src/data/articles/index.ts` was:

```ts
return [...sameCategory, ...rest].slice(0, limit);   // limit = 3
```

That returns the first three articles **in array order**, so every article in a
category linked to the same three. In the Hosting category (18 articles) all 18
pointed at the same 3, and the other 15 received no inbound link from any
related module.

Measured on the built site:

| | Before | After |
|---|---|---|
| Orphaned pages (0 inbound) | 0 | 0 |
| Pages with 1–2 inbound links | **34** | **2** |
| Articles with exactly 1 inbound link | **18** | **0** |

The fix walks the same-category list **cyclically** from the article's own
position, so in a category of *k > 3* every article links to the 3 that follow
it and therefore **receives exactly 3**. Padding for the two-article categories
(AI, Ecommerce) starts at a slug-derived offset so it does not recreate the
same concentration in miniature.

It is deterministic by requirement, not preference: these pages are statically
generated, so the link graph must be byte-identical across builds.
`Math.random()` would have been a bug.

The two remaining 2-inbound pages are the AI and Ecommerce categories, which
hold two articles each. That is the structural floor, not a defect.

## 10. Error handling — ONE REAL DEFECT, FIXED

`app/error.tsx` and `app/global-error.tsx` **did not exist**. Any unhandled
render error fell through to Next's built-in page: unstyled, no header, no
navigation, and on the client the bare string *"Application error: a
client-side exception has occurred."*

The SEO consequence is not the status code — Next sends 500 correctly — it is
that the default page contains no markup identifying itself as an error. A
visitor leaves instantly and the page reads as thin rather than as a failure.

Both boundaries now exist and reuse the 404's recovery shape. `global-error.tsx`
renders its own `<html>`/`<body>` and uses **only inline styles**, because the
layer it catches failures in is the one that loads `globals.css` and the fonts.

## 11. Analytics — absent by decision, not by omission

No analytics platform is installed. `data/cookie-policy` states plainly that
nothing in the analytics category runs, and `lib/consent` exists to keep that
promise. `lib/sera/analytics.ts` defines the event vocabulary and gates any
future sink behind consent, so connecting a platform is one `forward()`
implementation rather than thirty call sites.

**No measurement ID was invented.** Adding one would have made the cookie
policy false.

## 12. Security signals relevant to SEO — no defects found

- **No secret shapes in the client bundle** — grepped `.next/static` for
  `sk-*`, `re_*`, `WHMCS_API_SECRET`, `SERA_SESSION_SECRET`: zero hits.
- No `NEXT_PUBLIC_*` values inlined into client chunks.
- Headers served and verified: CSP, `X-Content-Type-Options`,
  `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`.
  HSTS is production-gated — correct.
- CSP `connect-src 'self'` means the browser cannot reach a third-party origin,
  which is also what keeps the no-analytics claim true at runtime.
- No open redirects: every `redirects()` destination is a same-origin literal.

## 13. Accessibility — no defects found at audit time

`scripts/a11y.mjs`: `smallTargets: []`, `navsWithoutLabel: 0`, `lang="en"`,
skip link present, logical heading order, one `<main>`.

One regression **was** introduced during this session's 404 rework — four
recovery links rendered 18px tall, under WCAG 2.5.8's 24px floor — and was
caught by that script and fixed to 44px before this audit ran.

## 14. Not verifiable from this environment

Stated rather than assumed:

1. **HTTPS, www → apex, and HSTS** are reverse-proxy behaviour. They cannot be
   tested against `127.0.0.1`.
2. **`/billing/*`** is WHMCS on cPanel, proxied at the same origin. `DEPLOY.md`
   documents it as the top cutover blocker; the link audit counts **76 login
   links, 21 sales-ticket links and every plan CTA** pointing into it.
3. **Search Console** — no property access exists in this environment. Nothing
   in this document claims verification or indexing has happened.
4. **Real-world Core Web Vitals** are field data. The figures in §7 are lab
   measurements under synthetic throttling.
